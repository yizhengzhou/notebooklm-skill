# 2026-08-27 方法論教訓紀錄

> 性質：這不是功能報告，是這一天在設計、執行、檢討 Persona 效果實驗的過程中，逼出來的一整套「怎麼做實驗、怎麼講結論」的規則。這些規則比任何單一實驗結果都更該被下一個 agent 記住，因為它們會決定下一次實驗還會不會犯同樣的錯。
> 對應的實驗本身見：`2026-08-27-persona-effect-experiment-plan.md`、`2026-08-27-persona-effect-experiment-final-report.md`。
> 溝通風格教訓另外記在 memory（`feedback_terse_precise_communication.md`），不重複寫在這裡。

## 一、關於「怎麼設計實驗」的教訓

1. **先跑小規模 pilot，再決定要不要放大。** 這次先跑 1 次（9 次呼叫），就抓到配額壓力題設計本身有漏洞（跟其他真實來源放同一個 Notebook，模型有「誠實的退路」可以借用不相關但真實的內容湊數，不會被逼到編造或拒絕的二選一）。如果一開始就直接跑 3 次重複（27 次），會在錯的設計上多花兩倍以上的成本才發現問題。
2. **要真正做到「獨立重複」，先確認工具真的能做到「全新對話」。** 查證後發現 `notebooklm-py` 的 `ask()` 不指定 conversation ID 時一定會延續現有對話，而本專案的 `EvergreenService.ask()` 雖然收了 `conversation_id` 參數，實際上從未傳給後端——這個 bug 影響了這個專案有史以來所有的 live 多輪測試（Case 1-3、strict-grounding 重現實驗），不是這次實驗獨有的問題。現在已修好（`ask --fresh`），但這件事本身證明：**不要假設一個「聽起來應該存在」的能力真的存在，要直接查證。**
3. **樣本數要花多少，取決於想偵測的效果多小，不是取決於「有沒有耐心」。** 用這次觀察到的變異程度（標準差約 5-10 個百分點）粗估：偵測 30 個百分點的大效果，n=3 已經足夠；偵測 10-15 個百分點的中效果，大約需要 n=10；偵測 5 個百分點的小效果，大約需要 n=40。樣本需求跟想偵測的效果大小平方成反比，不要在沒有算過的情況下說「多跑幾次就好」。

## 二、關於「量測本身可能是問題」的教訓

4. **量測工具本身如果不可靠，重複再多次也不會變準。** 這次的評分（引用支撐率、因果跳躍率、誠實標示率）是另一個 agent 用 LLM 自己讀答案、自己判斷句子分類算出來的，這個評分方法本身從未被獨立驗證過（沒有跟另一個獨立評分方式對照、沒有檢查一致性）。協調者只抽查了一份原始回答，沒有重新推導整套評分規則——這正是這個專案一路以來反覆抓到的錯誤（相信自動化判斷、沒有回頭核對），這次在最後一步又犯了一次。**下次要嘛驗證評分方法本身的可靠度，要嘛不要把它當成可以拿去做統計判定的數字。**
5. **引用標記存在，不代表引用內容正確。** Group 3 被明講「每個主張都要標引用」，自然會多貼引用標記，但這次的評分沒有去查證每個標記是不是真的指對來源內容——這正是這個專案更早之前修 citation offset 問題時就該學到、卻在這次評分設計裡又忽略的同一件事。

## 三、關於「這種實驗到底能不能證明什麼」的教訓（最重要的一組）

6. **LLM 本身有隨機性，加上模型可能被 provider 悄悄更新，代表任何一次固定實驗的數字，都不能保證在其他使用者、其他問題、其他時間點重現。** 這不是樣本數不夠的問題——就算樣本數增加到 1000、10000，也無法讓一次性、範圍固定的實驗結果變成「放諸四海皆準」的通則。這是外部效度（external validity）的根本限制，不是統計檢定力（power）的問題，兩者要分清楚，不要用「多測幾次」去回應一個「這種問題本來就無法一次實驗定案」的質疑。
7. **「每次都」這種語言，本質上跟「這是隨機的」互相矛盾。** 隨機的東西沒有「每次都」，只有「這幾次觀察到的都是」。以後描述任何有限次數的觀察，禁止使用「每次」「總是」「一定」這類全稱語氣，只能描述已經發生過的具體次數。
8. **不要用「有出現差異」直接推論「不是隨機」。** 一個現象在小樣本裡重複出現，可能是真的效果，也可能只是雜訊剛好長得像規律，或是一個很平凡的機制造成的（例如：叫模型標引用，它就照做，格式改變，這不代表 Persona 本身有什麼深層的因果力量，只是在遵守格式指令）。看到規律不能跳過「這可能只是巧合或平凡機制」這一步就直接下因果結論。
9. **不要用「常識、顯而易見」當理由跳過驗證。** 這次一度想以「叫模型去推測，它當然會亂猜」為由，主張某個問題等級不需要測試——後來被指出這個態度違反這整個專案一路堅持的原則：任何關於黑盒模型行為的假設，包括聽起來理所當然的，都該被驗證，不該被直覺取代。

## 四、關於「在有限資源下該怎麼做決定」的教訓（最終定調）

10. **放棄用單一實驗去追求「統計上可推廣的證明」，改成：做一次有限的實驗，誠實列出限制，把原始觀察直接交給使用者自己判斷。** 這不是偷懶，是正確認清這類問題的本質——不管加碼多少樣本，都無法把一次性觀察變成放諸四海皆準的保證，與其假裝可以做到，不如老實承認做不到，把「有限的證據」原樣交出去，讓使用者自己決定要不要參考。
11. **「這次實驗沒有測出統計上站得住腳的效果」，不等於「應該放棄給建議」。** 使用者仍然需要一個寫 Persona 的起點；不給建議，對使用者來說比給一個「未經證實但講清楚限制」的建議更不負責任。**建議可以繼續給，但理由要換成工程原則（例如「標引用是為了讓答案可以被查核」），不要包裝成「這樣做能讓某個指標改善幾個百分點」這種經不起換一批使用者驗證的話。**
12. **實驗結論即使是「沒有測到效果」，也不構成移除一個產品參數的理由。** 這次雖然沒有測到 Persona 強度影響幻覺率，但確實測到 Persona 影響引用格式的結構化程度——這已經是一個真實存在（雖然效果不大）的差異，不構成「Persona 完全沒用、應該拿掉」的證據。

## 五、關於 Persona 該怎麼設計的具體結論（已寫入 SKILL.md，此處記錄推導過程）

13. Persona 的設計空間至少有這幾個互相獨立的維度，一開始只想到「用途」是不夠的：用途／領域、跟使用者的互動姿態（指導型專家／教練／夥伴）、輸出格式、不確定時要迴避還是要標明信心給建議、要不要意識到自己過去做過的判斷（對應這個專案的 Evergreen 核心賣點）。
14. **判斷一個設定該放 Persona 還是該放進單一問題的原則**：只有「這個設定必須對這個 Notebook 未來每一個問題都成立」才放 Persona；如果換一個問題、換一個情境，這個設定可能就不一樣了，就該放進那次的問題文字裡，不要寫死在 Persona——不然會製造「Persona 跟 prompt 重疊」的混淆變數問題（這個問題本身也是這個專案更早的實驗中已經踩過的坑）。

## 六、給下一個 agent 的具體提醒

- 看到這份文件裡列出的教訓，不代表可以跳過重新驗證——這些是「上次犯過的錯」，不是「已經證明為真的定律」，用同樣的懷疑態度對待它們。
- 如果要重新評估 Persona 的效果，先解決第二節（量測工具本身未驗證）的問題，再考慮要不要重新設計實驗，不要直接加樣本數。
- 今天用掉的即時測試資源（Notebook、Deep Research quota、多次 `ask` 呼叫）已經不算少，這份文件本身就是要避免這些資源花的教訓被遺忘、下次重新用同樣的錯誤方式再花一次。
